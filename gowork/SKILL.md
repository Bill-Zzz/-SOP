# 开工（gowork）

## 1. 先确认再动手
- 收到任务，用自己的话复述五项：目标、范围、交付物、放在哪、不做什么。一次问完。
- 用户说“开始 / 去做 / 按这个来”之前只读不写：不建或改文件、不动 Drive、不起会改东西的 Agent。只读盘点可以。
- 哪项没确认，就再问那一项，不自己补。
- 做到一半发现和确认的不一样，停下来报。
- 用户说“不给反馈就自主完成”：待定项按默认定下，写进回复。例外：删文件、写正式环境、对外发送、合并 PR，仍要问。

## 2. 设计时怎么谈
- 先问后答。一次一个问题，给选项和我的倾向。先问用户怎么用，再问流程，最后问结构。
- 减法优先。第一版只做最基础的，能减不加，想加先问。
- 用用户的词，用户说不喜欢就换。
- 回复短，一次说一件事。

## 3. 谁来做
角色、Drive 衔接、并发上限见同目录 `协作与衔接.md`。规则绑角色，不绑某个 AI，谁都能接手。
- 贵的模型做判断和审稿，具体操作和机械活交给便宜的。派给谁看 Drive 的执行资源表，写进任务书。
- 细则由布置任务的人定：页数、章节、图表、版式写进任务书"本次细则"，不变原则只有 `协作与衔接.md` 第 1 节那四条。
- 任务书不另审，除非用户要看。

### 省 token
- 每篇最多四张工单，整阶段派，不按小步派；几步能完成的活不派。
- 工单只给文件路径，不转述数字；回复只要摘要与打回单。
- 判断的人不读脚本原始输出、不读格式规范、不读 Drive 目录。
- 打回后只改、只复查打回的位置，不重写、不重查全篇。

## 4. 交给子 Agent 时
- 任务书写：目标、要读的文件路径、已定设计（照做不改）、不做什么、收尾方式。只要摘要回复，不贴全文。
- 任务书里“放在哪、叫什么、怎么上传”只写“按 research-delivery”，不自写目录结构；交付核对由 research-delivery 跑 `check_delivery.py` 到通过。
- 互不依赖、不改同一批文件的活可同时开多个执行者，各一份任务书，最后由我汇总对账；有先后依赖的按顺序。并发上限看 Drive 的执行资源表。
- PR 只建不合并；用户说合并后我用 `gh api repos/…/pulls/<n>/merge -X PUT` 合。
- 同一仓库同一时间只一个执行者。Agent 中断后用 SendMessage 让它对账后接着做。
- 只能在用户自己电脑上做的数据活（富途导出等）：给用户一段可粘贴的任务文字，由用户交给那台电脑上的 AI。

## 5. 环境
- SOP 仓库：GitHub `Bill-Zzz/-SOP`（或自己的 fork）。改版本同时改 VERSION、CHANGELOG、LESSONS，跑 `bash tests/run_tests.sh`。环境禁用 `gh pr create` 时用 `gh api …/pulls -X POST`。
- 用 Google Drive 时，按 Drive 里的规则做。
- 用户对报告不满意时改 SOP，再按底稿局部重跑。
